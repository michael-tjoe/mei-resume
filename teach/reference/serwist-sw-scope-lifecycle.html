Compressed map of how this resume’s service worker registers, what it can control, and when a new version takes over.

Scope

script URL: /serwist/sw.js
default max scope: /serwist/
+ header Service-Worker-Allowed: /
→ registration may use scope /

Sources: web.dev (default scope), MDN Service-Worker-Allowed.

Lifecycle flow

register → download/parse
→ install (precache __SW_MANIFEST)
→ [waiting if old SW still has clients]
→ activate (cleanup; clients.claim if configured)
→ fetch / push / sync…

Update check (byte-diff of SW script) → new install in parallel → waiting until zero old clients or skipWaiting().

This app’s knobs

skipWaiting: false
New worker waits. User (or “close all tabs”) promotes it. Avoids instant mid-session swap.
messageSkipWaiting()
Posts SKIP_WAITING; Serwist calls self.skipWaiting(). Used by UpdateToast Refresh.
clientsClaim: true
On activate, claim open clients so they become controlled without relying only on a later navigation.
controlled vs in-scope
In-scope = URL under registration scope. Controlled = navigator.serviceWorker.controller is set; fetches go through the worker.
