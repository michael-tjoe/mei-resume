Why z-index lost — morph on perfect overlap

One idea: a transform on the panels track traps in-panel z-index. A body-portaled fixed nav wins the paint war — so we morph its color when the sticky rail perfectly overlaps it.

~7 minutes · tied to DesktopNavbar + panelsRef x translate

The failure mode you hit

Portfolio mounts a sticky invert rail (#portofolio-nav-rail). The global nav is createPortal(..., document.body) + position: fixed. Raising the portfolio section’s z-index did nothing useful: the panels row already has a GSAP transform: translateX(...).

Per MDN transform and the CSS Transforms spec: any non-none transform creates a stacking context and a containing block for descendants. Nested z-index only sorts inside that context; the whole transformed subtree paints as one unit against siblings / the root. (MDN: stacking context.

Body-portaled fixed chrome lives outside that transformed unit, so it stays on top of every panel — including a “higher” portfolio z-index.

The pattern that shipped

Don’t fight paint order. Change the fixed nav’s surface when geometry says the dark rail has docked:

// rail = #portofolio-nav-rail
rail.getBoundingClientRect().left <= 1  →  bg-brand-dark
rail.getBoundingClientRect().left > 1   →  bg-brand-tan
  • Perfect overlap = rail flush with viewport left (left ≈ 0), not early intersect (left ≤ 72).
  • Keep the sticky invert copy mounted (double-paint when aligned is OK).
  • Sync with IntersectionObserver + scroll/resize (GSAP scrub moves the rail without always “feeling” like a discrete event).

Feel it

Drag progress. Tan strip = body-portaled fixed nav (always on top). Dark rail rides the transformed track. When rail.left ≤ 1, the fixed strip morphs dark (~300ms).
