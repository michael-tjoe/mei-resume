Lesson 03 · useMorphSvgHover

Stale async hover race

One idea: when MorphSVG loads after enter/leave, older promises must not win — that is what loadGenRef + hoveredRef enforce.

~6 minutes · tied to useMorphSvgHover.ts lines 81–101

Why this hook exists

Chalk icons (Game, Mic, Paint) morph SVG paths on hover via MorphSVGPlugin. The plugin is loaded only on first hover through loadMorphGsap() so MorphSVG stays out of the initial bundle (GSAP plugins are opt-in). Hover is a user interaction, so the morph lives in event handlers — not in an Effect that would re-run on unrelated renders (Separating Events from Effects).

Full hook map (refs, return value, effects): reference — useMorphSvgHover.

The bug without a generation

loadMorphGsap() returns a Promise. Enter and leave can both fire before the first import resolves. Without a guard, this happens: 

enter → start load (want final)
leave → start load (want original)   // still waiting…
enter’s then() resolves → morphs to final   // WRONG: mouse already left
leave’s then() resolves → morphs to original

Your pointer is outside, but an older “enter” callback still animates to the hover shape. That is a classic stale async race.

What your morph does

hoveredRef.current = wantHover;
const gen = ++loadGenRef.current;

void loadMorphGsap().then((gsap) => {
  if (gen !== loadGenRef.current) return;       // newer call superseded us
  if (hoveredRef.current !== wantHover) return; // desire flipped mid-flight
  // … kill tweens, run animateFinal or animateOriginal
});

Each call stamps a new generation. When a promise settles, it only animates if it is still the latest stamp and the desired hover flag still matches what that call asked for. See the source: useMorphSvgHover.ts.
