Lesson 06 · Serwist digression

Scope decides where; lifecycle decides when

One idea: this app’s worker at /serwist/sw.js controls the whole origin only because the response header widens scope — and updates wait for you because skipWaiting: false.

~8 minutes · tied to app/sw.ts, SerwistProvider, UpdateToast

The map in this repo

  • SerwistProvider registers swUrl="/serwist/sw.js" in production only.
  • app/serwist/[path]/route.ts builds app/sw.ts and serves it (with the scope-widening header).
  • app/sw.ts: skipWaiting: false, clientsClaim: true, precache + runtime caches.
  • UpdateToast listens for waiting, then messageSkipWaiting() on Refresh.

Scope — who can this worker control?

Per web.dev lifecycle, default scope is ./ relative to the script URL. A worker at /serwist/sw.js would normally only control /serwist/* — useless for a site-wide PWA.

MDN: Service-Worker-Allowed lets the server broaden that path. Serwist’s Turbopack route sets Service-Worker-Allowed: / on the SW response (see Serwist Turbopack docs), so registration with site-wide scope is allowed.

Once a page is in scope and controlled, its navigations and fetches can go through the worker (your NetworkFirst pages, CacheFirst static assets, offline document fallback).

Lifecycle — when does it take over?

From Jake Archibald’s lifecycle article:

  1. install — first event; Serwist precaches self.__SW_MANIFEST (and fails the install if that promise rejects).
  2. waiting — if an older worker still controls tabs, the new one sits here until those clients go away or someone calls skipWaiting().
  3. activate — safe to clean old caches; with clientsClaim: true, Serwist claims open clients so they become controlled without needing a second navigation in many cases.
This app sets skipWaiting: false on purpose. Serwist still listens for a SKIP_WAITING message — UpdateToast’s Refresh button calls messageSkipWaiting(), then reloads on controlling. That matches the “user chooses when to flip” pattern in the Serwist class docs.
